# Internationalization — Vietnamese and English

Vote System localizes system-owned frontend copy in Vietnamese and English. User-generated ballots and profile bios remain exactly as authored.

## Supported locales

```text
vi  Vietnamese — default
en  English
```

The runtime uses `vi-VN` for Vietnamese formatting and `en-VN` for English formatting. The application updates `<html lang>` without remounting the product shell.

## Locale strategy

The application intentionally does not use locale-prefixed routes. One static Next.js application is wrapped by `I18nProvider`, and the active locale is React context state.

Guest resolution order:

1. read the browser-local `vote.locale` value;
2. use it when it is exactly `vi` or `en`;
3. otherwise use the first supported primary language from `navigator.languages` or `navigator.language`;
4. otherwise default to `vi`.

Examples:

```text
en-US -> en
vi-VN -> vi
fr-FR, en-US -> en
unsupported or unavailable -> vi
```

Storage failure is tolerated. Browser-language detection and the in-memory locale continue to work when local storage is unavailable.

## Persistent and in-memory changes

Locale changes have two intentional modes:

- Manual VI/EN switching writes `vote.locale` and updates the UI immediately.
- Authenticated bootstrap applies `profile.preferredLocale` in memory once for the resolved user without overwriting the guest's stored local preference.

When the authenticated profile is cleared through logout, logout-all, expiry, or failed refresh, the UI resolves the guest locale again from `vote.locale`, browser language, and then the Vietnamese default.

Saving a locale through Edit Profile is an explicit user action. It persists the backend `preferredLocale`, updates `vote.locale`, and applies the saved locale immediately.

## Catalog structure

Catalogs live at:

```text
frontend/src/shared/i18n/messages/vi.json
frontend/src/shared/i18n/messages/en.json
```

They use matching typed domains:

```text
common
auth
ballots
profile
admin
comments
notifications
errors
```

Machine-owned status, role, provider, category, avatar, locale, and error values remain stable language-neutral codes. Components translate labels at the presentation boundary.

## Formatting

Use the helpers exposed by `useI18n()`:

- `t(domain, key, variables)` for catalog copy and interpolation;
- `formatDate(...)` for dates and times;
- `formatNumber(...)` for counts and numeric values;
- `formatRelativeTime(...)` for relative timestamps.

Do not hard-code new user-facing system copy in feature components.

## Profile preference

The backend profile persists `preferredLocale` as `vi` or `en`, and auth bootstrap responses include it.

The frontend applies the profile locale once per authenticated user. Later manual switching in the same session is not overwritten by repeated renders or refreshes for that user. A different resolved user receives their own preferred locale.

## Verification

Frontend test and build commands run the catalog and locale-policy verification:

```bash
cd frontend
npm test
npm run build
```

The checks cover:

- both catalog files parse;
- required domains exist;
- Vietnamese/English key paths match;
- saved local preference precedence;
- browser-language fallback;
- Vietnamese default fallback;
- one-time authenticated bootstrap application;
- manual override preservation;
- user changes and logout boundary;
- immediate profile-save application.

Visual QA must cover both locales when a feature introduces or materially changes user-facing copy.

## Product rules

- Localize system UI, validation, empty states, notices, errors, accessible labels, and metadata.
- Do not auto-translate user-generated ballots, bios, future comments, or messages.
- Add Vietnamese and English copy in the same PR as every new user-facing feature.
- Keep backend/domain values stable and language-neutral.
- Do not store rendered notification text when a structured type and payload can be localized at read time.
